About PhishLens

API: checking...

PhishLens reads the subject and body of an email and says whether it looks like phishing, how sure it is, and which words pushed it to that answer. It is built to help a security analyst sort a queue of reported emails: it ranks and explains, and a person still decides.

It was built as the ITRI625 Machine Learning project at North-West University (2026) by Colile Sibanda. The sections below go from a short overview to the full technical detail; open any of them to read further.

How the parts connect

One trained model, one API in front of it, and three ways to use it. Every client sees the same verdict because every request goes through the same code path.

  1. Data pipeline (offline): six public email collections are cleaned, de-duplicated and split into training, validation and test sets.
  2. Training and evaluation (offline, in Jupyter notebooks): the Text-CNN is trained with early stopping, evaluated once on the test set, and explained.
  3. The API (FastAPI): loads the trained model once at start-up and answers /predict and /explain.
  4. The clients: this browser UI and the Tkinter desktop app call the API over HTTP; the notebook UI can run the same model in-process.
  5. Hosting: the API and this UI run in a Docker container on Render, rebuilt from GitHub on every change.
What happens when you click Analyse email
  1. The page sends your text to POST /predict and shows the verdict as soon as it returns, then sends it to POST /explain for the highlighted words.
  2. The security layer checks the request rate for your address and, for explanations, the rate across all users. Over the limit, the answer is HTTP 429 with a Retry-After header.
  3. The request schema rejects blank text (HTTP 422, naming the text field) and text over 50 000 characters (HTTP 413, stating the limit).
  4. The text is normalised: lower-cased, HTML removed, links replaced by <url>, addresses by <email>, numbers by <num>.
  5. It is split into tokens and each token is mapped to its vocabulary index (unknown words map to <unk>), then padded or cut to 400 tokens.
  6. The Text-CNN produces one score (a logit); a sigmoid turns it into the probability of phishing, and the verdict is phishing at or above the decision threshold.
  7. For the explanation, LIME scores 1 000 variations of the email with words removed, fits a simple model to how the probability moves, and gives each word a signed weight.
  8. Each weight is attached to every occurrence of its word with character offsets into the normalised text, and the page shades exactly those characters.

Technical details

Each section explains one part of the system: what it does, why it is built that way, and where its code lives in the repository.

Data: sources, cleaning, de-duplication and the split

The data is the Kaggle phishing email dataset, which pools six public collections: CEAS-08, Enron, Ling, Nazario, Nigerian Fraud and SpamAssassin, about 82 000 emails. Label 1 is phishing or spam, 0 is legitimate. Only the subject and body are used; sender, date and URL columns are kept out of the model because they carry archive-specific residue.

Cleaning strips HTML, joins subject and body with a separator, drops empty or near-empty rows and two rows that are mailbox parser residue rather than emails (src/phishlens/data/cleaning.py).

The pooled collections overlap: the same scam template appears many times with only a name or an amount changed. A random split would put near-copies on both sides and inflate every score. So each email gets a content hash computed after aggressive normalisation (lower case, no digits, no punctuation), emails with the same hash form a group, and whole groups are assigned to a split: 70% training, 15% validation, 15% test, stratified by label (hashing.py, splitter.py). The split is drawn once, written to disk and reused by every model.

The model: a Text-CNN, and the baseline it is compared with

M1, the served model, is a convolutional network for text (Kim, 2014) written in PyTorch: a 128-dimensional word embedding over a 40 000-word vocabulary, three parallel 1-D convolutions of width 3, 4 and 5 words with 100 filters each, ReLU, max-over-time pooling, dropout 0.5, and one linear output. The filters act as phrase detectors ("verify your account"), and max-pooling makes the model indifferent to where in the email a phrase appears (src/phishlens/models/text_cnn.py).

M0, the baseline, is TF-IDF over words and word pairs into logistic regression (models/baseline.py). It is the number M1 has to beat, and it comes close: most of the signal in this data is which words appear.

Training: the loop, patience and best-weight restore

Training is an explicit PyTorch loop (src/phishlens/training/loop.py), shown in full in notebooks/03_train_cnn.ipynb. Each epoch logs accuracy, precision, recall, F1, macro-F1, AUC-ROC and loss for training and validation to a CSV.

Early stopping watches validation macro-F1 with a patience of 3 epochs: an improvement smaller than 0.001 does not count. The best epoch's weights are saved whenever the score improves and restored when training stops, so the model that is evaluated and served is the best one, never simply the last one. The positive class is weighted to balance the training set, and every source of randomness is seeded from one value in the config.

Evaluation: the threshold, the test set, and the honesty checks

The decision threshold is chosen on the validation set to maximise macro-F1, then applied unchanged to the test set, which is used once, at the end (notebooks/04_evaluate.ipynb). Results are reported at that threshold and at 0.5.

A high score on pooled collections can come from recognising which archive an email came from rather than phishing. Two checks measure this. A corpus probe trains a simple classifier to predict the source collection from the text: it succeeds most of the time, so archive markers are present (tests/critical/test_corpus_probe.py). A leave-one-corpus-out evaluation trains on five collections and tests on the sixth: scores drop, and that drop is the honest estimate of performance on mail from a new source (notebooks/05_loco.ipynb). Both are in the report next to the headline numbers.

Explanations: LIME, character offsets and the Integrated Gradients cross-check

LIME (Ribeiro et al., 2016) treats the model as a black box: it removes words at random, watches the probability, and fits a small linear model whose weights become the word weights. It runs on the normalised text with the project's own tokeniser, so the words it weighs are exactly the words the model saw. The explanation is local: it describes this one email, not the model in general.

The alignment step (src/phishlens/explain/attributions.py) walks the text's own tokens in order and attaches each weight with start and end character offsets. Tests prove the offsets on repeated words, words inside other words and the placeholders.

As a cross-check, Integrated Gradients (Sundararajan et al., 2017, via Captum) attributes the model's score using its own gradients against an all-padding baseline. The two methods agree closely on short emails and less on long ones, where LIME's sampling is thinner (notebooks/06_xai.ipynb).

The API: endpoints, validation and model loading

The API is FastAPI (src/phishlens/serving/), started by run_api.py. At start-up it loads the vocabulary, the best checkpoint and the validation-selected threshold once; requests never reload anything. It has four endpoints: GET /health, GET /metadata (model id, threshold, seed, training commit, vocabulary hash, dataset version), POST /predict and POST /explain. Interactive documentation is at /docs.

The model is reached through one prediction function that LIME, the API and the notebooks all share, so an explanation always describes the deployed pipeline. Errors are returned as messages that name the problem, never as stack traces.

Security: what protects the public service
  • Rate limits per client address: 30 scoring requests and 6 explanations a minute, plus 30 explanations a minute across all users, because each explanation costs real CPU time. The client address is read from the proxy chain counting only trusted hops, so a forged X-Forwarded-For header cannot dodge the limit.
  • At most 16 concurrent connections; more get HTTP 503.
  • Security headers on every response, and on these pages a content security policy that allows only this site's own files: no third-party script, style or font.
  • Email text is placed in the page with textContent, never as HTML, so pasted content cannot run script. No CORS, so other sites cannot read the API's answers.
  • Nothing you paste is stored. The container runs as a non-root user, the dependencies are audited for known vulnerabilities, and the repository holds no credentials.
Deployment: Docker on Render, built from GitHub

render.yaml declares one free web service built from deploy/render/Dockerfile: Python 3.11, CPU-only PyTorch and only the serving dependencies, then the code, the config, the trained model, its vocabulary and its threshold file. Data and notebooks never enter the image. A small config override sets the address and port, so no serving code changes between local and hosted runs.

Render rebuilds and redeploys on every push to the main branch. The free instance has a fraction of one CPU and 512 MB of memory: the service uses about 300 MB at rest and about 410 MB under load. An explanation takes about a minute there (a few seconds on a laptop), which is why the verdict is shown first. After 15 idle minutes the service sleeps, and the next visit takes about a minute to wake it.

The three clients: browser, desktop and notebook

Browser UI (src/web/): plain HTML, CSS and JavaScript with no build step and no third-party code, served by the API itself at /ui/, so it is always the same origin as the API.

Desktop app (src/desktop/, run_app.py): Tkinter, calling the API over HTTP on a background thread so the window never freezes, with a live API status indicator and readable error messages.

Notebook UI (notebooks/07_analyst_ui.ipynb, src/notebook_ui/): analyse(text) or an interactive panel, running the model in-process with no server, or calling a running API.

None of the clients contains model code; all three render the same response, and all three show the same caution that the model assists and does not decide.

Testing and reproducibility

More than 200 automated tests run with pytest. A critical subset guards the results themselves: no content-hash group crosses two splits, metrics match values worked out by hand, early stopping restores the best epoch, and explanation offsets land on the right characters. The notebooks are committed with every output visible, and a script checks that only the evaluation notebook ever reads the test set.

Every metric file records the code commit, the seed and a hash of the split configuration, and /metadata reports the same for the served model, so any number or screenshot can be traced to the code that produced it.
